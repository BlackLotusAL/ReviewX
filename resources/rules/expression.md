# 表达要求

正文使用中文纯文本，模型输出结构化 JSON。
每条意见的 description 是单段、1–2 句、最多 120 字符的简述，只说明成因与核心后果。详细证据、调用路径、范围和触发条件放入 locations/impact，不在简述中叙述复核过程。
标签仅使用固定中文分类并去重：功能回归、逻辑错误、边界条件、异常处理、并发安全、资源管理、数据一致性、输入校验、安全风险、性能问题、规则违反、接口契约、单位换算、兼容性。tags 可空，不加 #，不使用英文标识符或框架名称。
每条意见恰好一个 kind=recommended 的完整推荐方案并放在 solutions 首位。方案包含 description 和非空 steps；同一方案中需要共同完成的文件修改分为步骤，不能把 C++、Python 等必要修改当成备用方案。仅存在可靠、可替代推荐方案的策略时增加 kind=alternative，并提供 applicability 说明适用条件和取舍，不强制备用方案。
具体代码修改优先在 solutions[].steps[].example 给出仓库实际语言的最小完整修复后源码，步骤必须标明目标仓库相对 path，使用已有函数与接口，每个文件分别展示；不输出统一 diff、伪代码、省略号或检视注释。新结果不使用方案级 example；该字段仅保留历史兼容。纯文档问题或无法可靠给出代码时提供可执行的文字步骤。
locations 的仓库相对路径、source/base 修订及起止行号必须与真实源码一致。宿主从固定版本提取片段，每处最多 40 行；不得依靠模型片段代替读取代码。
每处位置必须提供非空 annotations，包含原始一基行号 line 和单段、最多 120 字符的中文 text，解释该行的问题；行号必须在 startLine 到 min(endLine, startLine+39) 内。更远的问题行另列位置。模型不编写注释语法，不在 snippet.code 中加入说明。宿主在代码块内、对应问题行前插入“检视注释·问题行 L行号”，支持单行注释的语言使用原生注释，JSON 等其他格式使用 text 围栏。标注行不占 40 行源码额度，原始 snippet 保持提取结果。源码读取失败仍在代码块内保留标注，仅记录警告。
标注、简述和影响须区分已观察事实与条件性后果，说明中的路径使用仓库相对路径。纯规则违反只描述已证明的违约；仅有常量定义且未发现调用方时，明确实际运行时影响无法确认，不推断请求、线程或连接等行为。没有调用方本身不导致检视未完整。
多文件位置按路径和修订分点展示，同文件同修订的多处位置归组。代码块前标明“带检视标注的源码”。解决方案使用“推荐方案”和“备用方案”，方案内部步骤编号。历史正文与报告不改写，展示、保存与发送共享同一份冻结正文。
章节顺序、严重级别标记、标签和代码围栏由固定脚本生成；不要要求模型改变 JSON 合同或 Markdown 骨架。
