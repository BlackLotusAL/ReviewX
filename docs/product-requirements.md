## 1. 文档目的

本文定义 ReviewX 的产品目标、用户、核心流程、功能需求、非功能需求、验收标准和版本范围。

具体的 OpenCode 运行方式、多智能体编排、CodeHub CLI 契约、worktree 管理、数据模型和部署方案见《[技术架构设计](./technical-architecture.md)》。

## 2. 背景与问题

人工 MR 检视通常存在以下问题：

- 检视质量依赖个人经验，不同检视者关注点不一致。
- 设计、业务和代码实现问题需要不同领域知识，单一检视者容易遗漏。
- 大量低价值格式意见会稀释真正需要修改的问题。
- 已发现的问题没有结构化沉淀，类似问题会在不同仓库反复出现。
- 团队缺少持续的质量趋势、问题热点和规则有效性数据。
- 开放 MR 数量增加后，人工检视时效难以保证。

ReviewX 使用 OpenCode 驱动多个专家智能体，对指定代码仓的开放 MR 进行持续检视，并将检视结果、案例知识和周期趋势统一沉淀。

## 3. 产品定位

ReviewX 是一个可私有化部署的多智能体 MR 自动检视系统：

> 自动发现新增或更新的开放 MR，由设计、业务和代码专家并行分析，经过证据验证后只发布一条最有价值的修改意见；同时生成 Markdown 检视文档、案例文档和周期质量报告。

ReviewX 由以下产品能力构成：

| 能力 | 产品价值 |
| --- | --- |
| 仓库初始化 | 建立对代码结构、架构、业务规则和技术规范的持续认知 |
| 自动 MR 检视 | 每天自动发现并检视新增或更新的开放 MR |
| 多专家分析 | 从设计规范、业务规则和代码正确性等角度独立检视 |
| 证据裁判 | 去重、验证和排序候选问题，只选择最高价值意见 |
| CodeHub 回写 | 将检视意见发布到对应 MR 或先保存为人工确认草稿 |
| Markdown 知识库 | 沉淀单次检视、问题案例、周报和月报 |
| Review Web | 查看任务进度、检视历史、案例和质量趋势 |

## 4. 产品目标

### 4.1 核心目标

1. 每天自动发现指定仓库中新增或发生变化的开放 MR。
2. 使用多个专家智能体并行分析同一个 MR。
3. 对候选问题进行证据验证、去重和价值排序。
4. 每个 MR head SHA 最多自动发布一条检视意见。
5. 没有高价值问题时明确返回 `PASS`，不为了产出而制造意见。
6. 检视意见必须包含代码位置、问题影响、修改建议、严重等级和问题 Tag。
7. 自动生成单次检视 Markdown 和问题案例 Markdown。
8. 按 7 天和 30 天生成团队质量报告。
9. 提供简单网页查看当前进度和历史结果。

### 4.2 非目标

ReviewX 初期不负责：

- 自动修改 MR 代码。
- 自动批准、合并或关闭 MR。
- 取代最终的人工业务和架构决策。
- 对整个仓库每天重复执行全量分析。
- 在带有生产凭据的环境中执行 MR 提交的任意脚本。
- 一次向 MR 发布大量风格或格式类意见。

## 5. 产品原则

1. **价值优先**：一条高价值意见胜过大量低价值意见。
2. **证据优先**：意见必须能够定位、解释和验证。
3. **允许无意见**：`PASS` 是有效结果。
4. **版本可追溯**：结果绑定 MR head SHA、知识版本、规则版本和 Agent 版本。
5. **默认只读**：专家智能体不能修改代码或直接发布评论。
6. **人类可反馈**：每条意见可以被确认、驳回或标记为已修复。
7. **知识可复用**：有效问题应转化为案例和可推广规则。

## 6. 用户与角色

| 角色 | 主要诉求 |
| --- | --- |
| 开发者 | 尽早获得具体、可信且可操作的修改建议 |
| MR 检视者 | 使用自动检视结果辅助判断，减少重复检查 |
| 技术负责人 | 观察模块、规则和问题类型的长期趋势 |
| 质量负责人 | 管理规则、严重等级、误报率和检视覆盖率 |
| 系统管理员 | 配置仓库、计划、凭据、并发和发布模式 |

## 7. 核心业务对象

| 对象 | 定义 |
| --- | --- |
| Repository | 被 ReviewX 管理的代码仓 |
| Knowledge Snapshot | 针对某个默认分支 SHA 生成的仓库认知快照 |
| Merge Request | CodeHub 上处于开放状态的合并请求 |
| Review Run | 针对一个 MR head SHA 发起的一次完整检视 |
| Expert Run | 某个专家智能体在 Review Run 中的一次分析 |
| Finding | 专家发现的一个候选问题 |
| Selected Finding | 经过证据裁判后选出的唯一待发布问题 |
| Review Case | 从有效问题生成的技术案例文档 |
| Periodic Report | 7 天或 30 天范围的聚合质量报告 |

## 8. 核心用户流程

### 8.1 仓库接入与初始化

1. 管理员添加 CodeHub 仓库及其检视配置。
2. ReviewX 克隆仓库并锁定默认分支版本。
3. 系统完成一次全仓初始化分析。
4. 系统生成仓库概览、架构、模块、业务规则、测试策略和规范映射。
5. 管理员确认仓库已经具备自动检视条件。

### 8.2 每日自动检视

1. 调度器按计划查询所有开放 MR。
2. 系统识别从未检视或 head SHA 已变化的 MR。
3. 系统为各 MR 准备隔离工作区和检视上下文。
4. 多个专家智能体并行分析。
5. 证据裁判验证候选问题并选择唯一意见或 `PASS`。
6. 系统生成检视文档和案例文档。
7. 根据发布模式，将结果保存到网页、回写 CodeHub 或同时执行两者。

### 8.3 人工反馈

1. 用户查看 ReviewX 意见和证据。
2. 用户将意见标记为“确认”“误报”或“已修复”。
3. 系统更新案例状态和质量指标。
4. 后续报告基于有效状态聚合，不将已驳回意见计为有效问题。

### 8.4 周期报告

1. 系统按 7 天或 30 天聚合结构化检视数据。
2. 系统计算覆盖率、严重度、问题类型、热点模块、复发和修复情况。
3. 报告智能体根据统计数据生成趋势解释与改进建议。
4. 系统输出 Markdown 报告并在网页展示。

## 9. 功能需求

### 9.1 仓库管理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PR-REP-001 | 管理员可以添加、启用、停用和配置 CodeHub 仓库 | P0 |
| PR-REP-002 | 首次接入时必须完成全仓初始化分析并记录 baseline SHA | P0 |
| PR-REP-003 | 默认分支变化后只更新受影响的仓库知识，不重复全量分析 | P1 |
| PR-REP-004 | 每次检视必须记录所使用的知识快照版本 | P0 |

### 9.2 MR 发现与任务管理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PR-MR-001 | 系统可以按固定计划查询指定仓库的开放 MR | P0 |
| PR-MR-002 | 系统只检视未处理或 head SHA 已变化的 MR | P0 |
| PR-MR-003 | 系统支持配置是否忽略 Draft、机器人 MR、目标分支和标签 | P0 |
| PR-MR-004 | 不同 MR 可以并行检视，并显示各自进度 | P0 |
| PR-MR-005 | 失败任务可以自动重试或由管理员手动重试 | P0 |
| PR-MR-006 | MR 在检视过程中更新时，旧结果不得发布 | P0 |

### 9.3 多专家检视

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PR-AI-001 | 每个 MR 至少由设计规范、业务规则和代码正确性专家分析 | P0 |
| PR-AI-002 | 各专家应独立输出结构化候选问题 | P0 |
| PR-AI-003 | 业务证据不足时，业务专家必须返回证据不足而不是推测 | P0 |
| PR-AI-004 | 系统必须对候选问题进行定位验证、去重和价值评分 | P0 |
| PR-AI-005 | 每个 MR head SHA 只能选出一条最终意见或 `PASS` | P0 |
| PR-AI-006 | 完整内部报告可以保留多个候选及其采纳或驳回原因 | P1 |

### 9.4 CodeHub 检视意见

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PR-PUB-001 | 系统支持 `web`、`mr_comment`、`both` 三种发布模式 | P0 |
| PR-PUB-002 | 意见必须包含代码文件、行号或明确的代码范围 | P0 |
| PR-PUB-003 | 意见必须包含问题、影响、修改建议、严重等级和 Tag | P0 |
| PR-PUB-004 | CodeHub 支持时优先发布为 diff inline 评论 | P1 |
| PR-PUB-005 | 同一 MR head SHA 不得重复发布相同自动检视意见 | P0 |
| PR-PUB-006 | 专家智能体不能直接获得 CodeHub 评论权限 | P0 |

### 9.5 Markdown 文档

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PR-DOC-001 | 每次 Review Run 生成 `review.md` | P0 |
| PR-DOC-002 | 存在 Selected Finding 时生成 `case.md` | P0 |
| PR-DOC-003 | 系统生成 7 天检视报告 | P0 |
| PR-DOC-004 | 系统生成 30 天检视报告 | P1 |
| PR-DOC-005 | 所有人类可读文档均采用 Markdown | P0 |
| PR-DOC-006 | 文档必须链接回原始 MR、代码位置和相关案例 | P1 |

### 9.6 Review Web

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PR-WEB-001 | 总览页显示待处理、运行中、成功、PASS 和失败数量 | P0 |
| PR-WEB-002 | 进度页显示 MR 当前阶段、耗时、重试和失败原因 | P0 |
| PR-WEB-003 | 用户可以按仓库、状态、严重度、Tag 和日期筛选历史 | P0 |

## 10. 检视意见规范

### 10.1 必填内容

最终意见必须包含：

- 标题。
- 严重等级。
- 一个或多个受控 Tag。
- 待修改代码的文件和行号。
- 问题说明。
- 具体触发条件或失败场景。
- 对业务或系统的影响。
- 可操作的修改建议。
- 置信度。
- 命中的规则 ID；没有匹配规则时允许为空。

示例：

```markdown
### [S1][correctness][transaction] 事务提交前提前发送成功事件

**位置**：`src/payment/PaymentService.java:184-189`

**问题**：事务确认提交前已经发送成功事件；如果事务随后回滚，下游会收到与真实状态不一致的通知。

**建议**：改为事务提交后的回调，或采用 transactional outbox，并补充事务回滚测试。

**置信度**：94%

**规则**：`JAVA-TX-004`
```

### 10.2 严重等级

| 等级 | 含义 |
| --- | --- |
| S0 Blocker | 明确的安全事故、数据损坏或大面积不可用风险 |
| S1 Critical | 高概率严重错误，需要合入前处理 |
| S2 Major | 真实的功能、性能或维护风险，建议合入前处理 |
| S3 Minor | 局部低风险问题 |

### 10.3 标准 Tag

```text
security
correctness
business-rule
concurrency
transaction
performance
resource-leak
compatibility
api-contract
architecture
maintainability
test-coverage
observability
```

允许增加 `domain:<name>` 形式的仓库级业务标签。

## 11. 文档产物要求

### 11.1 单次检视文档

`review.md` 至少包含：

- MR 元数据和 base/head SHA。
- 检视时间和执行状态。
- 使用的 Agent、规则和知识版本。
- 各专家结论。
- 最终意见或 `PASS`。
- 候选问题的采纳或驳回原因。
- CodeHub 发布结果。
- 耗时、Token 和成本。

### 11.2 案例文档

`case.md` 至少包含：

- 仓库、MR、规则、Tag、严重度和案例状态。
- 变更背景。
- 问题代码和失败链路。
- 复现方式或测试用例。
- 推荐修复方式。
- 可以推广的检视规则。
- 后续确认、驳回或修复记录。

### 11.3 周期报告

7 天和 30 天报告至少包含：

- 扫描 MR 数、成功数、PASS 数和失败数。
- 严重度与问题类型分布。
- 仓库、模块和规则热点。
- 重复问题、新出现问题和典型案例。
- 确认率、误报率、修复率和平均修复时长。
- 下周期优先改进的规范、测试或工具。
- 模型成本和任务耗时。

## 12. 非功能需求

### 12.1 准确性

- 发布意见的文件和行号必须真实存在。
- 发布意见必须与本次 MR 变化有直接因果关系。
- 未达到质量阈值时必须返回 `PASS`。
- 统计指标必须由结构化数据计算，不能由模型估算。

### 12.2 安全性

- CodeHub 读取权限和评论权限必须分离。
- 专家智能体不能访问评论 Token。
- MR 内容、评论和源代码均视为不可信输入。
- 执行测试时必须使用无生产凭据的隔离环境。
- 凭据不得出现在 CLI 参数、日志或 Markdown 中。

### 12.3 可靠性

- 任务、游标和发布状态必须持久化。
- 服务重启后可以恢复或安全重跑未完成任务。
- 评论发布必须具备幂等保护。
- 发布前必须确认 MR head SHA 未变化。

### 12.4 性能与成本

- 每天可以枚举所有开放 MR，但只检视新增或变化的 head SHA。
- 仓库初始化后采用增量知识更新。
- 系统支持限制 MR 并发数、专家并发数和总模型会话数。
- 系统记录每次检视的耗时、Token 和模型成本。

### 12.5 可观测性

- 每个 Review Run 和 Expert Run 都有稳定 ID。
- 网页和日志可以关联 OpenCode session ID。
- 失败必须记录阶段、错误类型、重试次数和最终状态。

## 13. 建议验收指标

| 指标 | MVP 建议目标 |
| --- | --- |
| 已配置仓库每日扫描覆盖率 | 100% |
| 重复自动评论 | 0 |
| 发布到过期 head SHA 的评论 | 0 |
| 评论文件和行号有效率 | 100% |
| 单次任务状态可追溯率 | 100% |
| 周报指标与结构化数据一致率 | 100% |
| 人工确认率 | 上线试运行后逐步达到 70% 以上 |
| 适用规模 MR 的 P95 检视耗时 | 建议不超过 20 分钟 |

人工确认率和耗时目标应在真实仓库试运行后重新校准。

## 14. 版本范围

### 14.1 MVP

- 一个 CodeHub 仓库。
- 全仓初始化与知识快照。
- 每日定时扫描开放 MR。
- 设计、业务和代码三个专家。
- 证据裁判与一条意见或 `PASS`。
- `review.md` 和 `case.md`。
- 7 天报告。
- 简单只读网页。
- CodeHub 评论使用 `dry-run` 或人工确认模式。

### 14.2 第二阶段

- CodeHub 自动评论。
- 人工确认、误报和已修复反馈。
- 30 天报告。
- 增量知识更新。
- Webhook 实时触发，定时扫描作为兜底。

### 14.3 第三阶段

- 多仓库和多技术栈。
- 团队与仓库权限治理。
- 规则质量、误报率和模型成本治理。
- 支持其他 Git 代码托管平台。

## 15. 待确认事项

- CodeHub 是否支持携带 base/head SHA 的 inline discussion API。
- 业务规则和历史案例由谁维护以及如何审批。
- S3 问题是否允许自动发布，或仅保留在内部报告。
- 自动评论上线前需要多少个 MR 的只读试运行样本。
- 不同技术栈是否使用不同模型、推理等级和超时。
