# ReviewX 产品需求文档（PRD）

Oct 15, 2026 · @Black Lotus

## 1. 文档说明

ReviewX 共 25 条需求（编号 R01–R26，其中 R20 空缺），按功能价值分为 P0 10 条、P1 10 条、P2 5 条，排列顺序见第 4 节（R26 位于 P1 末位）；MVP 覆盖 P0 + P1 共 20 条。

- **来源**：ReviewX 原始需求（`original-requirements.md`）。
- **外部依赖**：远端代码仓操作通过 [CodeHub CLI](https://github.com/BlackLotusAL/CodeHubX/blob/main/docs/PRD.md#4-%E4%B8%9A%E5%8A%A1%E5%91%BD%E4%BB%A4) 完成，拉取代码使用本机 Git，AI 检视由 OpenCode 执行。

**术语**

| 术语 | 含义 |
| --- | --- |
| 检视 | 对一个 MR 发起的一次 AI 检视，按第 5 节 R11 的 7 个步骤执行 |
| 报告 | 一次检视成功完成后保存的结果，包含结论和全部意见 |
| 意见 | 报告中的单条检视意见，可发送为 MR 评论 |
| 处理记录 | 用户对每条意见的决定（发送或不发送）及其发布结果（已发布、发布失败、结果未知），见 R08、R16 |
| 候选 | 查找阶段提出、尚待验证的疑似问题，验证成立后才成为意见（R10） |
| 最新报告 | 某 MR 最近一次成功保存的报告（R16） |
| 报告页 | 在 MR 列表点击 MR 打开的抽屉，显示该 MR 的报告和意见，顶部可切换历次报告（R16） |
| 规则 | 用户维护的检视关注点（R26） |
| 本次使用的规则 | 检视某 MR 时，全局与该项目已启用、且适用文件与本次变更匹配的规则；只有这些规则加入提示词（R26） |
| 关注面 | 查找阶段划分检视方向的配置项，每个关注面对应一个查找会话（R10）；与规则是不同概念 |
| 代码缓存 | 每个项目在数据目录下的本地仓库，用于增量拉取代码（R11） |
| 检视副本 | 每次检视从代码缓存导出的完整代码，供 OpenCode 只读查阅，检视结束即删除（R11） |
| 数据目录 | ReviewX 保存报告、处理记录、代码缓存、规则和诊断日志的本地目录（R13） |
| 诊断日志 | 供排查问题的运行日志（R21） |

## 2. 产品概述

ReviewX 是运行在本机的 CodeHub 辅助检视工具：AI 负责找问题，用户决定什么发出去。

**目标用户**：在 CodeHub 上做代码检视的个人开发者，单人、本机、通过网页使用；运行于 Windows。

**性能目标**：单个 MR 的检视在 15 分钟内完成，口径见 R11。

**核心原则**

- **人工掌控**：关注哪些项目、何时获取 MR、检视什么、何时停止、发布哪条意见，全部由用户主动触发。
- **AI 只建议**：AI 产出意见，是否采纳和发布由用户逐条决定。
- **结果可信**：未完成或失败的检视不能冒充完成，发布结果必须如实反映。
- **记录不丢**：报告和处理记录只追加、不覆盖，重启后仍可追溯。

**核心流程**

1. 添加关注项目
2. 手动获取开放 MR
3. 选择 MR 发起 AI 检视，查看进度
4. 阅读报告，逐条发送或不发送意见
5. 回看历史结果与处理记录

## 3. 价值分级方法

分级只看一个问题：去掉这条需求，用户还能不能安全地完成「发现 MR → 检视 → 发布」闭环。

| 等级 | 定义 | 去掉后的后果 | 排期 |
| --- | --- | --- | --- |
| P0 必须 | 核心闭环或安全底线的组成部分 | 产品无法使用，或会误发评论、泄露凭据 | MVP |
| P1 重要 | 明显影响可用性与可信度 | 能用但体验差、易误判，用户需大量绕路 | MVP |
| P2 增强 | 提升效率与可追溯性 | 少数场景不便，可由人工或 CodeHub 替代 | 第二迭代 |

同级内按三项排序：对闭环的贡献 > 失败时的风险 > 使用频率。

按价值从高到低排列，各等级条数见第 1 节。

| 编号 | 需求 | 等级 | 排序理由 |

| R01 | 对选中 MR 的整体代码变更发起 AI 检视，进入串行队列，不设规模上限 | P0 必须 | 产品存在的理由 |
| R02 | 每条意见包含问题描述、严重程度（四级）、代码位置 | P0 必须 | 缺位置和严重程度，意见无法判断或发布 |
| R03 | 用户逐条点击发送后，才经 CodeHub CLI 发布为 MR 总评论 | P0 必须 | 防止误发，是人工掌控的底线 |
| R04 | 手动并行获取关注项目的开放 MR，单个项目失败不影响其余 | P0 必须 | 检视的入口 |
| R05 | 添加、查看关注项目，并校验项目有效 | P0 必须 | 获取 MR 的前提 |
| R06 | 凭据不在页面、报告、诊断日志中泄露，不交给 AI | P0 必须 | 泄露后果不可逆 |
| R07 | 失败或中断的检视不算完成，不完整结果不可发布 | P0 必须 | 防止基于残缺结果误发 |
| R08 | 如实显示发布结果：已发布、失败、结果未知；未知项核对后标记，失败项可手动重发 | P0 必须 | 误判会导致漏发或重复发 |
| R09 | 报告和外部内容安全渲染，不暴露本机文件 | P0 必须 | AI 输出和 MR 内容均不可信 |
| R10 | 意见按结构化模板输出：问题描述、位置、影响分析、解决方案、预防措施 | P0 必须 | 缺少影响分析和解决方案，意见难以直接发布 |
| R11 | 检视状态与 m/n 进度实时可见 | P1 重要 | 检视耗时长，需知道是否卡住 |
| R12 | 停止进行中的检视，主动停止不报为故障 | P1 重要 | 避免浪费时间和模型额度 |
| R13 | 报告与处理记录持久化，重启后可用 | P1 重要 | 否则重启即丢失工作 |
| R14 | 报告关联项目、MR 和代码版本，MR 更新时间变化时提示 | P1 重要 | 判断意见是否过时的依据 |
| R15 | 未发现问题时给出明确结论并保留报告 | P1 重要 | 区分「没问题」和「没跑完」 |
| R16 | 逐条决定发送或不发送，支持其余全部不发送，MR 列表提示待处理条数 | P1 重要 | 提醒用户哪些 MR 还没处理完 |
| R17 | 失败时说明影响、原因、失败步骤和下一步，按失败类型决定是否停止队列 | P1 重要 | 减少用户自行排查 |
| R18 | 一键打开对应的 CodeHub MR 页面 | P1 重要 | 核对上下文与评论，成本极低 |
| R19 | 重新检视，新报告不覆盖旧报告；同一 MR 不可重复发起 | P1 重要 | MR 更新后需要再检视 |
| R26 | 自定义检视关注点：规则管理、按项目启用、效果反馈与沉淀 | P1 重要 | 让检视能力随使用持续迭代 |
| R21 | 诊断日志保留 30 天、总量不超过 100 MB | P2 增强 | 排障用，非日常 |
| R22 | 移除关注项目，历史保留，重新添加后可见 | P2 增强 | 低频，不移除也不影响使用 |
| R23 | 意见按需附代码示例 | P2 增强 | 多数意见无需示例 |
| R24 | 撤销最新报告中的「不发送」决定 | P2 增强 | 纠错场景，频率低 |
| R25 | 取消队列中尚未开始的检视 | P2 增强 | 排队中的检视可能等待较久 |

## 5. 需求详细说明

每条需求列出验收标准与设计规则。

### 5.1 P0 必须（R01–R10）

**R01 发起 AI 检视**

- 验收：用户在 MR 列表选中一个 MR，可发起针对其整体代码变更的检视；获取 MR 不会触发检视。
- 队列：发起后检视进入全局 FIFO 串行队列，同一时间只执行一个。
- 变更范围：按目标分支与源分支的分叉点比较（三点差异），只包含源分支自分叉后的改动，与 CodeHub MR 页面显示的变更一致；不设变更规模上限。
- 上下文范围：差异按函数边界给出上下文，每处改动附带所在函数的完整代码，减少 AI 为理解改动而发起的查阅。
- 排除文件：配置项「排除文件类型」支持扩展名（如 `.png`、`.min.js`）和完整文件名（如 `package-lock.json`、`go.sum`）两种写法，只匹配文件名、不匹配目录；默认清单为：锁文件 package-lock.json、npm-shrinkwrap.json、yarn.lock、pnpm-lock.yaml、Cargo.lock、go.sum、poetry.lock、Pipfile.lock、composer.lock、Gemfile.lock；压缩产物与映射 .min.js、.min.css、.map；图片 .png、.jpg、.jpeg、.gif、.bmp、.ico、.webp、.svg；字体 .ttf、.otf、.woff、.woff2、.eot。二进制文件按内容自动识别并排除。检视副本保留全部文件，但 AI 检视时不能读取按扩展名或文件名排除的文件（R10）。
- 上下文预检：步骤 5 按字符数估算提示词规模，包括差异、MR 标题、提交说明和本次使用的规则，不含检视副本。规模超过配置项「模型上下文上限」的 25% 时，判为「检视失败 · 步骤 5/7 变更超出模型上下文」，不调用 OpenCode。其余上下文留给 OpenCode 的系统提示与工具定义、AI 按需查阅的文件和输出的意见。
- 无可检视的变更：排除文件后差异为空时，跳过步骤 6、不调用 OpenCode，直接在步骤 7 保存报告，结论为「无可检视的变更」（R15），按检视完成处理。

**R02 意见核心要素**

- 验收：每条意见有问题说明和严重程度；能定位时给出文件与行号。
- 严重程度：severity 取 fatal、major、minor、suggestion 四级，展示规则见 R10。

**R03 逐条确认后发布**

- 验收：只有用户对某条意见点击发送，ReviewX 才把它作为评论发到对应 MR；不存在批量自动发布入口。
- 实现：调用 CodeHub CLI 的 `mr comment create`，传入正文和 severity，发为 MR 总评论；代码位置写在正文的「问题位置」段。
- 逐条发送：每次点击只发送一条；发送期间其他「发送」按钮置灰，同一时间只调用一次 CLI。
- 与检视并行：发送独立于检视队列，检视执行期间仍可发送已完成报告中的意见。
- 结果判定：CLI 返回成功记为已发布，明确失败记为发布失败，返回 `WRITE_RESULT_UNKNOWN` 记为结果未知。CLI 不保证幂等，ReviewX 不自动重试，后续处理见 R08。

**R04 手动获取开放 MR**

- 验收：用户点击「获取 MR」后，列出已关注项目的开放 MR，显示所属项目、标题和本次获取时间；获取 MR 与检视队列、评论发送相互独立。
- 并行获取：全局最多同时执行「并发数」个 CLI 调用（配置项）。先串行完成第一个项目，再并行处理其余项目，避免多个 CLI 进程同时刷新 DevUC token。列表按项目添加顺序展示。
- 按项目原子更新：一个项目的 MR 列表和详情全部取得后才替换该项目的结果；某项目失败时跳过它继续其余项目，失败项目保留上次成功的结果。
- 项目状态：每个项目显示「获取中 / 已更新 / 获取失败」；失败时给出原因和上次成功时间，并提供只重取该项目的「重新获取」按钮。
- 进度与汇总：获取期间显示「项目 m/n 完成 · k 个失败」，「获取 MR」按钮置灰；结束后显示「已更新 m/n 个项目，k 个失败」。

**R05 添加并校验关注项目**

- 验收：用户输入数字 Project ID 后，ReviewX 通过 CodeHub CLI 确认项目存在且可访问，才加入关注列表；列表以仓库完整路径显示项目名称。
- 格式校验：输入为空或不是正整数时，本地即时提示「Project ID 应为正整数」，不调用 CLI。
- 重复添加：ID 已在关注列表中时不调用 CLI，提示「该项目已在关注列表中：仓库路径（ID）」，并在列表中定位、高亮该项目。
- 重新添加：曾移除的项目校验通过后恢复关注，提示「已恢复 N 份历史报告」（R22）。
- 校验失败：按原因提示——项目不存在或无访问权限、CodeHub CLI 未登录（请重新登录）、网络不可用；失败不改变关注列表。

**R06 凭据保护**

- 验收：访问凭据不出现在页面、报告和诊断日志中。
- CodeHub 凭据：由 CodeHub CLI 登录后保存在系统 Credential Helper；ReviewX 只调用已登录的 CLI，不接收、不保存。
- Git 凭据：拉取代码使用用户本机已配置的 Git 凭据（凭据管理器或 SSH 密钥），ReviewX 不读取、不保存；Git 认证失败按环境级错误处理（R17）。
- 交给 AI 的内容：OpenCode 的输入、运行环境和检视副本中不含任何代码仓库凭据、Git 配置或相关环境变量；模型服务认证由 OpenCode 自身配置。

**R07 不完整结果不冒充完成**

- 验收：失败、中断或未成功保存的检视显示为对应状态，不生成可发布意见。

**R08 发布结果如实反馈**

- 验收：每条已尝试发布的意见显示为已发布、发布失败或结果未知之一；发布失败与结果未知时提示用户到 CodeHub 核对。ReviewX 不自动重试。
- 结果未知：用户核对后标记为「已发布」或「确认未发布」。标记只改本地状态、不调用 CLI，记为人工确认，与 CLI 返回的结果区分；「确认未发布」转为发布失败。
- 发布失败：用户排除原因（如重新登录 CLI、恢复网络）后可点击「重新发送」，每次点击只调用一次 CLI，结果仍按 R03 判定。
- ReviewX 关闭：发送过程中 ReviewX 被关闭的意见，重启后记为结果未知。
- 范围：标记与重新发送只对最新报告（R16）中的意见开放。

**R09 安全渲染**

- 验收：报告、MR 标题等外部内容以纯文本或净化后显示，不执行脚本；页面不能读取数据目录以外的本机文件。
- 链接与图片：意见中的链接只显示为纯文本，不可点击；图片不加载，显示为「\[图片\] 地址」文本。渲染时不发起任何外部请求。

**R10 结构化检视意见模板**

- 验收：AI 只输出结构化字段，不直接写 Markdown；ReviewX 按下方模板把字段渲染为评论正文，标题信号灯和展示等级与 severity 一致。
- 检视流程：步骤 6 由 ReviewX 调度多个 OpenCode 会话，分查找、合并、验证三个阶段完成，最后把验证成立的意见生成报告（排列顺序见 R16）。
  - 查找：为配置项「关注面」中的每个关注面各开一个会话并行执行，每个会话只负责一个关注面。会话用 `report_candidate` 提交候选（严重程度、标题、怀疑内容、位置、依据），不写完整意见，也不要求完全确定。
  - 大 MR 分片：差异提示词超过配置项「分片阈值」时，按文件把差异切成大小均衡的若干片，片数 = 提示词规模 ÷ 分片阈值（向上取整），默认配置下最多 2 片。同一目录的文件尽量放在同一片，单个文件不拆分。每个关注面对每一片各开一个查找会话，同时运行的查找会话不超过配置项「查找并行数」。每个会话另含其他分片的概要（变更文件清单和每处改动所在的函数名），但在权限上禁止读取其他分片的差异文件；需要了解跨文件调用关系时，查阅检视副本中的源码。
  - 合并：ReviewX 把同一文件中行号相距 3 行以内的候选合并为一个，并去除跨分片的重复候选，不调用 AI。
  - 验证：候选按文件分组，每组最多 5 个，最多配置项「验证并行数」个会话并行。每个候选必须处理一次：成立的用 `report_finding` 提交完整意见，并附「文件:行号」依据；不成立或无法确认的用 `reject_candidate` 说明理由。被否决的候选及理由写入诊断日志，不进入报告。
- 提示词：
  - 内容：本次差异（R01）、MR 标题、变更范围内的提交说明和本次使用的规则（R26），不含 MR 描述。查找会话另含所负责关注面的说明，验证会话另含待核实的候选。提交说明从代码缓存读取，不调用 CodeHub。
  - 检视方法：要求 AI 先通读差异，列出需要核实的疑点（查找会话为本关注面的疑点，验证会话为给定的候选），再在同一轮中一次发出多个查阅，避免逐个查阅拉长轮数。
  - 查阅范围：每次查阅都要对应差异中的一个具体疑点，如被修改代码的调用方和被调用方、引用的定义、类型、样式和配置、相关测试。不做浏览目录、通读无关文件等探索性查阅，也不为确认第三方库或框架的行为而查找其源码。
  - 输出语言：由配置项「输出语言」决定；代码、标识符、文件路径和错误信息保持原文。
  - 意见数量：不设最低严重程度和数量上限，四级意见全部输出。
- 会话运行：
  - 启动方式：每个会话通过 `OPENCODE_CONFIG_CONTENT` 注入配置，以 `opencode run --format json` 运行并关闭标准输入，工作目录为检视副本（R11），不修改用户自己的 OpenCode 配置。注入配置关闭自动上下文压缩，避免查阅结果被摘要替换；上下文仍然溢出时按「步骤 6 上下文超限」处理（R17）。
  - 错开与重试：各会话共用 OpenCode 本地数据库，同时启动的会话依次错开约 1.5 秒。OpenCode 进程在会话开始前退出时，等待后重试启动，最多 2 次，仍失败按「OpenCode 报错」处理。该重试只针对进程启动，不重新执行检视。
  - 模型：使用用户 OpenCode 的默认模型，ReviewX 不指定。
  - 版本：只支持 OpenCode 1.18.x，其他版本的工具与权限配置方式不同，无法保证只读限制。步骤 6 开始前检查版本，不符合时判为「检视失败 · 步骤 6/7 OpenCode 版本不受支持」，按环境级错误处理（R17）。
- 只读与越权：
  - 权限：通过 OpenCode 权限配置默认拒绝全部工具，只放行 `read`、`glob`、`grep` 和本阶段的提交工具；禁止读取「排除文件类型」（R01）中的文件，禁止访问检视副本以外的目录。AI 不能改动代码、执行命令或访问网络，需要查看调用方、定义或配置时在检视副本中按需查阅。
  - 越权监控：运行中逐条检查 OpenCode 事件流中的工具调用，出现白名单以外的工具立即终止整个子进程树，判为「检视失败 · 步骤 6/7 越权调用」。
- 提交与校验：
  - 提交工具：ReviewX 以本地 MCP 服务提供提交工具。查找会话可用 `report_candidate` 和 `finish_review`，验证会话可用 `report_finding`、`reject_candidate` 和 `finish_review`。
  - 即时校验：每次调用提交一项，按字段定义即时校验；不通过时返回具体错误（哪个字段、原因），AI 在同一会话内修正后重新提交。同一候选只能处理一次，`finish_review` 之后的提交一律拒绝。ReviewX 只采信校验通过的提交，不解析 AI 回复中的文本或 JSON。
  - 校验口径：只把模板必需段设为必填，文本长度不设上限，未知字段忽略。
  - 失败：任一会话收尾（R11）后仍未调用 `finish_review`，或有候选未被处理，判为「检视失败 · 步骤 6/7 检视未完成」，已提交的候选和意见不保存为报告（R07）。收尾时输出又因长度上限被截断的，失败原因写明「模型推理超出输出上限」。后续处理见 R17；原始输出脱敏后写入诊断日志。

### 5.2 P1 重要（R11–R19、R26）

**R11 检视状态与进度可见**

- 验收：检视状态为排队中、检视中、停止中或已结束（检视完成、检视失败、已停止），进度与可用操作随状态更新，无需整页刷新。
- 进度以「m/n」表示当前项与总数，分三层：
  - 队列：「排队中 · 第 m/n 位」，n 为当前队列长度。
  - 步骤：「步骤 m/7 · 步骤名」；报告页列出全部 7 步，已完成步骤显示耗时。
  - 步骤内：有可数对象时追加「对象 m/n」，否则显示已运行时长。

| 步骤 | 名称 | 步骤内提示 |
| --- | --- | --- |
| 1/7 | 读取 MR 信息 | 已运行时长 |
| 2/7 | 拉取源分支 | 已运行时长 |
| 3/7 | 拉取目标分支 | 已运行时长 |
| 4/7 | 校验 MR 未变化 | 已运行时长 |
| 5/7 | 生成变更快照 | 文件 m/n |
| 6/7 | OpenCode 检视 | 「查找 m/n · 候选 k 个」或「验证 m/n」，并显示已运行时长 / 上限，如「验证 2/3 · 06:10 / 12:00」 |
| 7/7 | 保存报告与意见 | 意见 m/n |

- 显示示例：MR 列表行显示「检视中 · 步骤 5/7 生成变更快照 · 文件 12/48」。
- 停止中：显示当前清理动作，如「正在停止 · 终止子进程」「正在停止 · 清理临时目录」。
- 失败：保留失败所在步骤，如「检视失败 · 步骤 3/7 拉取目标分支」；失败后队列如何处理见 R17。
- 时限与收尾：
  - 检视时长：验收目标为每个 MR 从步骤 1 开始到报告保存不超过 15 分钟，不含排队时间。该目标不作为运行时的失败条件，超时判失败只由步骤 6 的「OpenCode 超时」负责。
  - 超时：步骤 6 总时长（含各会话收尾）超过配置项「OpenCode 超时」即终止全部会话，判为「检视失败 · 步骤 6/7 超时」。
  - 收尾触发：每个会话单独收尾，且只收尾一次。出现以下任一情况时，ReviewX 中断该会话的 OpenCode 运行，在同一会话内追加收尾指令，要求 AI 提交尚未提交的内容后调用 `finish_review`：
    - 到达本阶段的收尾时间：从步骤 6 开始计，查找阶段为配置项「查找收尾时间」，验证阶段为配置项「验证收尾时间」；
    - 该会话上下文达到收尾阈值；
    - 单次输出因长度上限被截断；
    - AI 结束回复但未调用 `finish_review`。
  - 收尾过程：收尾阶段只开放提交工具，关闭全部查阅工具，收尾前已提交的内容保留。查找阶段最迟在收尾时间后 2 分钟结束，届时未完成的查找会话按未完成处理（R10）。步骤 6 的进度显示「收尾中」。
  - 收尾阈值：每个会话的阈值 = min（该会话提示词规模 + 配置项「查阅额度」，配置项「安全上限」），提示词规模取该会话第一轮请求的实际上下文。查阅额度按模型上下文上限的比例设置，使不同大小的 MR 都有相同的查阅空间；安全上限为单次输出上限 32K 和最后一轮查阅结果留出余量。
- 代码准备：
  - 代码缓存：每个项目在数据目录下保存一份不含工作区的本地仓库，项目尚无代码缓存时以部分克隆创建。步骤 2、3 只拉取该 MR 的源分支和目标分支，并固定到当时的提交；允许非快进更新，源分支变基后强制推送时以远端最新内容为准。Windows 上启用 Git 长路径支持。
  - 检视副本：从代码缓存导出源分支在本次提交上的完整代码到临时目录，作为 OpenCode 的工作目录；不含 .git 和 Git 配置，检视结束即删除。
  - 缓存损坏：拉取失败且判断为缓存损坏时，该检视失败并提示清除代码缓存。关注列表提供「清除代码缓存」按钮，下次检视时重建；ReviewX 不自动删除重建。

**R12 停止进行中的检视**

- 验收：进行中的检视可被停止；停止后显示「已停止」，不计为故障，不产生可发布意见。
- 停止过程：检视先进入「停止中」，终止该检视的整个子进程树并清理检视副本等临时目录，完成后转为「已停止」。本文其他位置所说的「停止」均按此执行。

**R13 结果与记录持久化**

- 验收：关闭并重新打开 ReviewX 后，已保存的报告和处理记录仍可见；未完成的检视不会自动继续。
- 重启恢复：ReviewX 关闭时处于排队中、检视中或停止中的检视，重启后显示「已停止 · ReviewX 关闭时中断」，不计为故障；队列清空，由用户重新发起。
- 资源清理：ReviewX 退出时终止自己启动的全部子进程树；重启时清理数据目录内残留的临时目录，不触碰数据目录以外的文件。
- 启动：在终端运行 `reviewx`，打印访问地址和当天的诊断日志路径，并用默认浏览器打开页面；浏览器打不开时服务照常运行，用户按地址手动访问。
- 停止服务：关闭浏览器不影响服务和检视；在终端按 Ctrl+C 停止服务，并执行资源清理。
- 单实例：同一台机器只运行一个 ReviewX；已有实例运行时再次启动，提示已在运行并打开现有页面。
- 端口与访问：使用配置项「端口」指定的固定端口，只监听 127.0.0.1，并校验请求来源，防止本机其他网页冒充用户发起操作。端口被其他程序占用时拒绝启动并提示更换端口，不自动换端口。
- 配置文件：以下配置项只通过配置文件修改，网页不提供设置页；启动时读取，修改后重启生效，格式错误时拒绝启动并指出出错项。
  - 端口（默认 17080，R13）
  - 数据目录（默认位于用户数据目录下；更改位置后不自动迁移旧数据，由用户自行移动，R13）
  - 并发数（默认 6，R04）
  - 排除文件类型（默认清单见 R01）
  - 模型上下文上限（默认 256K tokens，R01、R10、R11）
  - 输出语言（默认中文，R10）
  - 关注面（默认 4 个：逻辑与状态、边界与错误处理、接口与一致性、测试与体验，R10）
  - 分片阈值（默认模型上下文上限的 20%，R10）
  - 查找并行数（默认 8，R10）
  - 验证并行数（默认 4，R10）
  - 查找收尾时间（默认步骤 6 开始后第 5 分钟，R11）
  - 验证收尾时间（默认步骤 6 开始后第 10 分钟，R11）
  - OpenCode 超时（默认 12 分钟，R11）
  - 查阅额度（默认模型上下文上限的 25%，256K 时约 64K，R11）
  - 安全上限（默认模型上下文上限的 75%，256K 时约 192K，R11；与单次输出上限 32K 之和须低于模型上下文上限）
- 数据升级：数据目录记录数据格式版本，启动时检查。发现旧版本时，先将数据目录（不含代码缓存）备份到 backups 下，按版本和日期命名，保留最近 3 份；再自动迁移索引与状态记录，全部写成功后才替换原数据，失败则拒绝启动、原数据不变，并提示备份位置和原因。检视报告内容不迁移、不改写。数据版本高于程序版本时拒绝启动，提示升级 ReviewX。
- Windows 适配：调用 CLI 时以参数数组传参，评论正文中的换行、引号和反斜杠保持原样；含中文和空格的路径可正常使用。

**R14 关联代码版本**

- 验收：每份报告记录以下内容，供追溯：
  - 所属项目和 MR、检视时的 MR 更新时间、源分支提交标识
  - 本次使用的模型名称（R10）
  - 本次使用的规则名称及内容快照（R26）
  - 被排除的文件清单（R01），列在报告末尾
  - 结论（R15）和全部意见
- 版本依据：以 CodeHub 返回的 MR 更新时间判断版本。源分支有新提交（含变基后强制推送）时该时间变化，新增评论不改变它。
- 版本提示：最近一次获取 MR 得到的更新时间与报告记录的不一致时，在 MR 列表和报告页提示「报告基于旧版本」；只提示，不拦截发送，不为此调用 CodeHub。

**R15 无问题的明确结论**

- 验收：检视完成时，报告结论为以下三种之一，三者互不混用，均照常保存报告：
  - 发现问题：列出全部意见。
  - 未发现问题：AI 检视过，没有意见（判定见 R10）。
  - 无可检视的变更：排除文件后没有内容交给 AI，AI 未检视（R01），待处理意见为 0。

**R16 意见处理状态与待处理提醒**

- 决定：每条意见只有一个决定——发送或不发送；「不发送」表示已决定不发布，而非稍后再看。
- 操作范围：只有最新报告（见第 1 节术语）中的意见可以发送、标记不发送、撤销（R24）、标记发布结果或重新发送（R08）。
- 归档：新检视成功保存报告后，旧报告转为只读，其中的待处理意见显示「已被新报告取代」，不再计入提醒。新检视排队中、进行中、失败或已停止时，旧报告仍是最新报告。
- 历次报告：报告页顶部的切换栏按时间从新到旧列出该 MR 的历次报告（只含成功保存的报告，失败或已停止的检视不列入），每项标注时间或状态，如「最新报告 · 11:47」「历史 1 · 已归档」；点击切换查看。
- 待处理：最新报告中既未发送也未标记不发送的意见。
- 提醒：MR 列表每行显示「N 条待处理」，为 0 时显示「已处理完」；报告页顶部显示同一计数，并可跳到下一条待处理意见。
- 离开 MR 列表：以最近一次获取 MR 的结果为准，MR 未再返回即视为离开，不区分关闭或合并，也不为此调用 CodeHub。离开后其报告和处理记录保留但不提供查看入口，待处理意见保持原状态、不计入提醒；MR 重新出现在 MR 列表时恢复入口和计数。
- 需核对：发布失败或结果未知的意见不计入待处理，另显示「N 条需到 CodeHub 核对」；标记为已发布或重新发送成功后移出该计数。
- 批量收尾：「其余全部不发送」将最新报告中所有待处理意见标为不发送，二次确认后执行，可通过 R24 逐条撤销。
- 排列顺序：意见按严重程度从高到低排列，同级内按文件路径和行号排列；「跳到下一条待处理」按同一顺序。不提供筛选。
- 验收：用户可只处理一部分后离开；再次打开 ReviewX 时，能从 MR 列表看出哪些 MR 还有待处理意见。

**R17 失败说明与下一步**

- 验收：失败提示指出受影响的项目、MR、意见或操作，给出原因和失败步骤，区分已完成、未执行和无法确认的部分，说明队列是继续还是已停止，以及用户可以手动做什么。
- 队列处理：检视失败时按下表决定是否停止队列，停止时其余排队中的检视转为「已停止」。

| 失败类型 | 示例 | 队列 |
| --- | --- | --- |
| 环境级错误（任何步骤） | CodeHub CLI 认证失败、Git 认证失败、网络不可用、OpenCode 版本不受支持 | 停止整个队列 |
| 步骤 1–5 的其他失败 | 读取 MR 失败、MR 在拉取期间已变化、缓存损坏、变更超出模型上下文 | 只影响该检视，队列继续 |
| 步骤 6–7 失败 | OpenCode 报错、超时或越权调用、检视未完成（会话未完成或候选未全部处理）、保存失败 | 停止整个队列，避免继续消耗 token |
| 步骤 6 上下文超限 | 预检未拦住、OpenCode 报出上下文超限 | 只影响该检视，队列继续；提示可拆分 MR 或改为人工检视 |

**R18 跳转 CodeHub**

- 验收：MR 列表和报告页都可直接打开对应的 CodeHub MR 页面。

**R19 重新检视不覆盖**

- 验收：对已检视过的 MR 可再次发起检视，代码版本未变化时同样允许；新报告独立保存，旧报告内容和处理记录不变，归档规则见 R16。
- 互斥：同一 MR 有检视在排队中、检视中或停止中时，「重新检视」置灰，该检视结束后恢复。

**R26 自定义检视关注点**

- 验收：用户可维护规则，检视时 AI 按本次使用的规则重点检查，规则的效果可以被观察和持续改进。
- 规则内容：每条规则是一份 Markdown 文本，包含名称、适用文件（如 `*.java`、`src/db/**`，留空表示全部）、检查要点、正例与反例。
- 管理：网页提供规则列表，可新建、编辑、复制、启用或停用、删除；规则文件保存在数据目录，用户也可直接用编辑器或 Git 管理。规则列表每次打开或刷新时重新读取规则文件，检视在开始执行时读取，外部修改无需重启即生效。格式错误的规则在规则列表中标为「格式错误」并说明原因；检视时跳过该规则并在报告中注明，不导致检视失败。
- 内置规则：首次使用提供一组通用规则（正确性、安全、性能、可维护性）作为起点，可停用或复制后修改。
- 作用范围：规则分全局与项目级；检视某 MR 时使用「全局启用规则 + 该项目启用规则」，其中只有本次使用的规则（见第 1 节术语）加入提示词，长度计入上下文预检（R01）。
- 意见关联：意见的 `rule` 字段（R10）取值限定为本次使用的规则名，由校验保证 AI 不能自造规则名；不属于任何规则的意见留空，计入「未归属规则」。
- 可追溯：报告保存本次规则快照（R14），修改规则不影响旧报告。
- 效果反馈：规则列表显示每条规则近 30 天的命中数、发送数、不发送数及采纳率。命中数指 `rule` 为该规则的意见数；发送数为用户点击发送的意见数，含发布失败和结果未知；采纳率 = 发送数 ÷（发送数 + 不发送数），待处理和「已被新报告取代」的意见不计入。
- 沉淀新规则：已发送的意见可一键「沉淀为规则草稿」，以该意见的问题描述和代码预填检查要点与反例，用户编辑确认后再启用。
- 验证修改：修改规则后，可对已检视过的 MR 重新检视（R19），在报告页切换查看新旧报告（R16）。

### 5.3 P2 增强（R21–R25）

**R21 诊断日志**

- 验收：检视、获取 MR、发布评论等操作写入诊断日志，不含凭据（R06），可供排查。
- 切分：按自然日切分，每天一个文件。
- 保留：30 天，总量不超过 100 MB。ReviewX 启动时和每天切出新文件时各清理一次：删除超过 30 天的文件，总量超限时从最旧的文件删起；当天正在写入的文件不删。
- 范围：清理只作用于诊断日志。

**R22 移除关注项目**

- 验收：项目可从关注列表移除，其报告和处理记录不删除；重新添加后可再次看到原有历史（R05）。
- 移除确认：弹窗列出受影响的检视，确认后执行。
- 活动检视：该项目执行中的检视按 R12 停止，排队中的检视移出队列，均转为「已停止」；处理完成后才完成移除。
- 评论发送中：移除按钮置灰，发送结束后恢复。
- 代码缓存：移除项目时一并删除其代码缓存。

**R23 代码示例**

- 验收：需要时意见附带说明问题或修复方式的代码示例，对应 R10 模板中的可选代码块。

**R24 撤销「不发送」**

- 验收：只有最新报告（R16）中标记为「不发送」的意见可恢复为待处理，并重新计入待处理提醒。

**R25 取消排队中的检视**

- 验收：队列中尚未开始的检视可被取消，取消后移出队列并显示为「已停止」。

## 6. 产品边界与非目标

以下内容明确不做，不参与价值排序。

| 类别 | 不做的事 |
| --- | --- |
| 使用范围 | 远程或局域网访问、多用户协作、登录与权限管理、多实例运行；Windows 以外的操作系统 |
| 检视执行 | 多个 MR 并行检视 |
| 自动化 | 定时或后台发现 MR、自动启动检视、自动发布评论 |
| 失败处理 | 检视与评论发布的自动重试（R10 的 OpenCode 进程启动重试除外）、补发、恢复；重启后自动继续未完成的检视 |
| 意见处理 | 自动判定并拦截过时意见；报告中相似或重复意见的提示与去重（R10 合并阶段对候选的去重除外）；新旧报告对比视图；编辑意见正文；自动修复代码；行内评论 |
| AI 能力 | R10 验证阶段以外的自动裁决；识别或标注代码中针对 AI 的指令 |
| 周边功能 | 统计看板、通知中心、网页设置页等与核心检视无关的功能 |

**数据底线**：报告与处理记录只追加，不因后续操作被覆盖或删除；R13 的数据升级只转换索引与状态记录的格式，迁移前完整备份。诊断日志按 R21 清理，代码缓存按 R11、R22 管理。

## 7. 成功标准与验收场景

用户能独立走完「发现 MR → 发起检视 → 阅读意见 → 自主处理 → 追溯结果」即为成功；下表列出每个场景依赖的需求。

| 场景 | 用户应获得的结果 | 依赖需求 |
| --- | --- | --- |
| 管理项目并获取 MR | 找到关注项目中的开放 MR，并能打开对应 CodeHub 页面 | R04、R05、R18、R22 |
| 发起和控制检视 | 主动开始、停止、重新检视，清楚进度与结果 | R01、R11、R12、R19、R25 |
| 阅读检视结果 | 无论有无问题都有完整报告；有问题时能理解位置、影响和建议 | R02、R10、R15、R23、R26 |
| 处理检视意见 | 每条发布的意见都来自明确操作；最新结果中的「不发送」可撤销 | R03、R08、R16、R24 |
| 回看历史 | 重新检视、移除项目或重启后，原有结果和记录仍可追溯 | R13、R14、R16、R19 |
| 失败或结果不确定 | 知道原因、影响和下一步；ReviewX 不自动重试，失败项可手动重发 | R07、R08、R17、R21 |
| 日常使用 | 凭据和本地数据受保护，阅读报告不执行危险内容 | R06、R09 |
| 检视时效 | 每个 MR 在 15 分钟内得到报告，或得到明确的失败原因 | R10、R11、R17 |
