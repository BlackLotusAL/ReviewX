# ReviewX 产品需求文档

## 1. 产品定义

ReviewX 是面向 CodeHub Merge Request 的 Windows 本机单用户代码检视工具。用户登记 Project、手动刷新 open MR 并开始检视；系统按全局 FIFO 运行只读 OpenCode 多轮会话，保存独立报告，等待用户逐条发送或跳过 Finding。

产品支持 Windows 10/11、Node.js 22 及以上版本，依赖本机 Git、CodeHub CLI 和已配置默认模型与认证的原版 OpenCode 1.18.30。支持环境不等于所有环境均已验证，验收必须注明实际平台和版本。

- 本机运行，仅监听 `127.0.0.1`，使用本机 CLI 与原生认证，不在网页中管理凭据。
- MR 发现、检视和评论发送由用户主动触发，不定时扫描、不自动检视、不自动评论。
- 检视全局串行；评论发送使用独立的全局串行通道。
- 成功报告不可变，历史 attempt、意见处理结果和日志持久保留。
- 失败不自动重试、补发或续跑，用户可以主动重新检视。

不提供远程部署、多用户或权限系统、Finding 正文编辑、自动修复、Judge、多 Agent、语义去重、发送前 MR 版本阻断、批量发布或舍弃、数据库及统计看板。

## 2. 入口、界面与操作

### 2.1 启动

唯一业务入口为无参数 `reviewx`。启动时创建服务日志、取得单实例锁、选择可用 loopback 端口，向终端输出访问地址与日志绝对路径，并尝试打开系统默认浏览器。

浏览器打开失败时服务继续运行，用户可手动访问；状态目录、日志或 HTTP 服务无法创建时启动失败。重复启动返回已有实例地址，不创建第二个服务。关闭浏览器不停止任务，退出服务进程才停止服务。

### 2.2 主工作台

主工作台由项目导航、按项目分组的 MR 列表、MR 详情抽屉组成。

- 项目导航按仓库路径组织可折叠目录；项目主体定位到本页对应分组，`#ID` 在新标签页打开项目网页，移除按钮独立操作。
- MR 列表展示标题、IID 外链、最近刷新的 `updated_at`、状态、队列位置、检视耗时及主操作。项目标题在分组范围内吸顶，导航定位不得遮挡目标。
- 队列弹窗展示任务与位置，内容在视口内滚动；支持触发器、外部点击及 Escape 关闭，并恢复焦点。
- 详情展示状态、阶段、错误、attempt 历史、Findings、完整报告和发布结果。列表及详情的 MR 外链在新标签页打开，点击不得同时触发抽屉。
- Findings 按返回顺序展示 severity、完整 Markdown、处理状态和卡片级动作。正文不可编辑，没有复选框或批量发布栏。
- 完整报告默认收起，首次展开才请求；收起保留缓存，再次展开不重复请求，切换 attempt 后重新默认收起。
- 支持键盘打开、历史切换、Escape 关闭和焦点恢复，遵循系统减少动态效果设置；长标题、代码和表格不得破坏可操作性。

### 2.3 状态、进度与耗时

| 状态 | 含义与操作 |
| --- | --- |
| 未检视 | 没有历史 attempt，可开始检视 |
| 排队中 | 位于 FIFO，可停止 |
| 检视中 | 准备代码、运行 OpenCode 或保存结果，可停止 |
| 停止中 | 等待取消和清理，不接受新操作 |
| 已停止 | 不自动恢复，可重新检视 |
| 检视失败 | 执行失败，可重新检视 |
| 待处理 | 最新 attempt 有 pending Finding，可逐条处理或重新检视 |
| 发送中 | 正在发送一条评论，该 MR 不可重新检视 |
| 已完成 | PASS 或全部 Findings 已发送/跳过，可重新检视；最新 attempt 可撤销跳过 |
| 发布失败 | 无 pending 且存在 failed、unknown 或 not_attempted，可重新检视；最新 attempt 可撤销跳过 |
| 已归档 | 被新 attempt 取代，只读 |

进度展示阶段、可信工具完成数、必需材料交付数及限制，不表示模型理解百分比。耗时从实际执行开始到检视结束，包含准备与清理，不包含排队、人工处理或发送评论；停止和失败同样固定结束时间。缺少可靠结束时间的历史记录不推算补齐，显示“—”；未开始的任务不显示耗时。

网页加载后立即读取本地状态，随后每秒轮询，同一页面不重叠请求；revision 变化时重读已打开的 MR 详情。轮询不调用 CodeHub、Git、OpenCode，不代替手动刷新。接口见 [API](API.md)。

### 2.4 辅助页面

- `/logs` 在新标签页展示当前会话日志，页面可见时每两秒读取。位于底部时跟随新增内容，阅读历史时保留滚动与选择；日志 API 提供原始文本。
- `/preview` 使用固定内存样例展示各状态、历史和报告，复用工作台组件。数据操作不发起变更请求，示例 CodeHub 外链不跳转；刷新后样例保持确定，日志入口仍指向本机会话。

## 3. 项目与任务生命周期

CodeHub 集成仅使用以下 CLI 命令，参数以独立 argv 传递：

```text
codehub repo view <project-id> --output json
codehub mr list --project-id <project-id> --state open --output json
codehub mr view <mr-iid> --project-id <project-id> --output json
codehub mr comment create <mr-iid> --project-id <project-id> --body <markdown> --severity <severity> --output json
```

### 3.1 项目登记与移除

Project ID 必须为十进制正整数字符串。添加时调用 `codehub repo view` 验证项目，保存 HTTPS clone URL、显示名称和项目网页地址；重复添加失败。名称取 clone URL 的完整仓库路径，项目按登记顺序持久化。

clone URL 必须为 HTTPS，且不含用户名、密码、查询参数或片段。项目 `web_url` 必须是字符串，原样保存，不做协议或凭据校验；这与 MR 网页地址的严格校验不同。项目地址缺失不降级，也不提供缺失该字段的项目数据迁移。

移除项目时，停止该项目正在执行的检视、取消其排队任务，等待清理后移除登记和主列表入口；其他项目不受影响。该项目正在发送评论时拒绝移除。快照、attempt、报告、发布记录及日志不删除，重新登记后恢复可见。移除不存在的项目失败。

### 3.2 手动刷新 MR

按项目登记顺序串行调用 `mr list --state open`，再按返回顺序调用每个 MR 的 `mr view`。列表项必须提供 IID 和非空标题；详情是 `updated_at`、分支、状态及 MR 网页地址的来源。仅处理 CLI 实际返回的列表，不假设覆盖全部 MR。

每个项目完整成功后原子替换快照。不再返回的 MR 从当前列表隐藏，历史保留。某项目失败即停止本次刷新：已成功项目保留新结果，失败及尚未处理项目保留上次快照。刷新不创建 attempt 或启动检视。

MR `state` 去除首尾空白、忽略大小写后接受 `open` 或 `opened`，其他值拒绝。MR `web_url` 必须为无用户名和密码的 HTTPS URL，缺失或非法时提示 CLI 不兼容。旧 MR 快照可以缺少 `webUrl`，下次成功刷新补齐；该兼容性不适用于项目字段。

刷新取得新版本不会自动重检或归档旧结果；在用户创建新 attempt 前，最新成功 attempt 的 pending Findings 仍可发送。

### 3.3 创建与调度

开始检视和重新检视均创建独立 attempt，追加到全局 FIFO 尾部。同一 MR 处于排队、检视、停止中或发送中时拒绝创建；非活动 MR 可以对相同 `updated_at` 重复检视，不按版本去重。

创建新 attempt 的同一状态事务中，旧 attempt 立即归档，旧 pending Findings 转为 archived；已发布、跳过、失败、未知和未执行记录保持原值，全部只读。新 attempt 随后失败或停止也不恢复旧结果的可操作性。

全局同一时间只执行一个检视。停止排队项时立即移出队列；停止执行项时进入停止中，取消 Git/OpenCode、等待进程退出并清理，最终转为已停止，其他排队任务可继续。

检视失败时当前 attempt 为检视失败，全部尚未开始的排队项转为已停止并清空队列。用户需主动重新建立队列。停止或失败不影响独立评论发送。

### 3.4 意见处理与发布

最新成功 attempt 的 pending Finding 提供“不发送”和“发送到 CodeHub”。不发送立即持久化为 dismissed 并记录时间；只要仍为最新 attempt，已跳过项可撤销为 pending，包括已完成或发布失败状态。历史 attempt 不可操作。

发送单击即执行，无二次确认。全局同一时间只允许一条评论命令，占用期间禁用所有 Finding 决策操作。目标 attempt 进入发送中，每次发布记录只含一个 ordinal，只发送该 Finding 的 severity 和 body。

发送前不检查 MR 版本或调用 `mr view`。用户通过外链和手动刷新判断适用性；已开始的评论不可停止，可与另一个 MR 的检视并行。

| Finding 状态 | 含义 |
| --- | --- |
| pending | 尚未处理 |
| published | CodeHub 明确确认成功 |
| dismissed | 用户跳过 |
| failed | CodeHub 明确返回失败 |
| unknown | 无法确认是否已写入 |
| not_attempted | 兼容旧多条批次中未执行的后续项，新单条发布不产生 |
| archived | 被新 attempt 取代的未处理意见 |

发送失败或结果未知只终结目标 Finding，不阻断其他 pending 项。发布结束或用户决策后统一归并：有 pending 为待处理；无 pending 且全部 published/dismissed 为已完成；无 pending 且有 failed/unknown/not_attempted 为发布失败。空 Findings 的成功检视为 PASS，直接已完成。

失败、未知和未执行项不提供网页重发，用户应到 CodeHub 核对，再处理其他意见或重新检视。

### 3.5 重启恢复

启动时将持久化为排队、检视或停止中的 attempt 转为已停止，清空活动检视队列，不自动续跑。中断发布的当前 Finding 恢复为 unknown，其他 pending 保持；旧多条批次后续未执行项恢复为 not_attempted，再按发布归并规则确定状态，不自动补发。

## 4. 多轮检视

### 4.1 固定范围与执行顺序

每个 attempt 使用独立会话，不复用旧上下文。仅支持同一 Project 内的 MR，CodeHub 契约不提供跨项目源仓库信息。

1. 调用 `mr view` 取得当前版本和分支。
2. fetch Git 对象，固定 source S、target T、唯一 merge-base B，建立 B→S 变更索引并冻结规则。
3. 再次调用 `mr view`；`updated_at` 或源/目标分支变化时失败，不启动 OpenCode。
4. 启动独立 OpenCode 原生会话，通过可信工具读取材料并提交候选结果。
5. 核对正式合同、范围、必需材料、实际交付收据及原生消息终态。
6. 关闭工具桥接、结束本次进程并清理临时对象，再检查取消状态。
7. 将报告、正式合同及执行记录在临时目录写齐，原子完成报告目录。
8. 在串行状态事务中再次检查取消并登记成功引用，此后才开放意见处理。

第三步之后 MR 再变化不使本次固定结果失效，新版本由用户刷新并重新检视。检视流程无评论写入口。

范围必须使用 B→S，不能以 T 代替 B，也不模拟合入最新 target 的结果；merge-base 不唯一时失败。索引包含固定 SHA、changeId、变更类型、旧/新路径、diff 页与哈希、行号映射及不可审原因；scopeHash 使用稳定序列化，不包含临时路径、时间或哈希自身。

只读 bare Git 树与 blob，不 checkout 或复制工作树，不执行 hooks、外部 diff、textconv、过滤器或子模块初始化。LFS 指针按 Git 文本处理，不下载实体。二进制、非法 UTF-8、symlink/submodule 或无法完整交付的变更阻断整次成功，不产生部分范围 PASS。

### 4.2 受控工具与证据

| 工具 | 用途 |
| --- | --- |
| `reviewx_index` | 分页读取变更清单、规则索引及必需基线 |
| `reviewx_diff` | 按 changeId 分页读取固定 diff |
| `reviewx_read` | 分页读取 source=S 或 base=B 的文件与行范围 |
| `reviewx_search` | 在固定树内进行字面搜索，定位未修改调用方 |
| `reviewx_rules` | 分页读取冻结规则 |
| `reviewx_submit` | 提交唯一正式业务候选 |

页码和搜索 offset 从 0 开始。必需材料包括所有索引、diff、规则页及删除/重命名旧路径的 base 文件页。每条 Finding 至少关联一个有效 changeId，每个关联变更须有对应 source 新路径或 base 旧路径证据；还可引用未修改调用方。

证据行号从 1 开始且为闭区间，必须由本会话对准确修订和路径的成功 `reviewx_read` 响应完整覆盖。diff 和搜索命中仅作导航，不能代替文件证据。交付以绑定 session/message/call 的实际响应及哈希为准，不以模型自述“已读”为准；交付不证明模型理解或结论正确。

### 4.3 规则配置

随包规则位于 `resources/review-rules/`，按安装位置解析，不依赖启动 cwd。可选本地配置为 `%LOCALAPPDATA%/ReviewX/rules/profile.json`，版本为 1：`resources` 登记资源路径及版本，`languages` 覆盖扩展名映射，`projects` 按 Project ID 指定额外资源。

- general 和 comments 始终选择；C++ 扩展名含 `.cpp/.cc/.cxx/.h/.hpp/.hxx`，Python 含 `.py/.pyi`。未知文本语言保留通用规则，Qt、PyQt5、PySide2 按项目显式启用。
- 依据变更旧/新路径稳定选择语言规则，之后追加项目规则并去重；自定义资源不得替换内置 ID。
- 缺少 profile 使用默认值；显式资源缺失、非法、越界或超限则失败，不静默回退。
- 自定义资源仅限 rules 目录内非空 UTF-8 本地文本，不经过链接或 junction；不支持远程下载、脚本、命令替换或递归 include，单文件不超过 1 MiB。
- 每次 attempt 冻结内容、版本、顺序及资源/profile 哈希，修改仅影响之后的 attempt。规则不能覆盖宿主权限、范围或合同。submittedPromptHash 仅代表宿主实际提交的提示，不代表全部原生 Prompt。

### 4.4 接受条件与限制

专用工具提交只产生 `SUBMITTED` 候选。只有完整材料与规则齐备、合同和证据有效、唯一候选归属正确、所有工具交付可核对、会话正常完成、进程退出与桥接关闭、无取消或错误时，才可最终 `ACCEPTED`。HTTP 200、退出码 0、idle 或单个工具完成均不能单独代表成功。

同一 message/call 的相同调用去重；重复标识参数变化或不同调用再次提交判为冲突。非法条目拒绝整个对象，不裁剪、丢弃坏条目、读取聊天 JSON 或另开格式修复会话。请求接收状态不确定时不盲目重发。

| 限制 | 上限 |
| --- | --- |
| 文本页 | 200 行，响应 32 KiB，文本预算 24 KiB |
| blob | 16 MiB |
| 完整 diff / 累计交付 | 各 64 MiB |
| 正式提交 | 1 MiB，100 条 Finding |
| 单条 body | 64 KiB |
| OpenCode 启动至关闭 | 共用 60 分钟预算 |

超长单行、必需页缺失、关键截断或预算耗尽不得当作完整检视。非关键搜索限制可记录并分页，无关未修改文件不单独阻断成功。取消优先原生 abort，再有界终止本次进程树，清理不影响独立评论通道。

## 5. 结果与持久化

### 5.1 正式合同

业务合同版本独立于状态文件版本。只接受专用工具提交的严格对象：

```json
{
  "contractVersion": "reviewx-review/1",
  "completion": "complete",
  "blockers": [],
  "findings": [{
    "severity": "major",
    "body": "Markdown 原始正文",
    "changeIds": ["宿主索引中的 ID"],
    "evidence": [{"revision": "source", "path": "src/example.cpp", "startLine": 1, "endLine": 2}]
  }]
}
```

completion 接受 complete/incomplete，但成功必须 complete 且 blockers 为空；合法空 findings 才是 PASS。severity 为 fatal/major/minor/suggestion。额外字段、非法枚举、范围、数量或大小均拒绝；body 必须非空白且不含 NUL，保留解码后的全部字符，不 trim 或改写。

### 5.2 评论规范与正文保真

以下骨架指导生成，不作为严格 Markdown 章节校验条件：

````markdown
### 🟠 Major: <问题标题>

**问题描述**：

- 严重级别：Major
- 标签：`#tag`
- 简述：<问题说明>

**问题位置**：`path/to/file:line-range`

```language
<相关代码>
```

**影响分析**：

- **直接后果**：<直接后果>
- **影响范围**：<影响范围>
- **触发条件**：<触发条件>

**解决方案**：

<可执行的解决方案，数量按问题需要>

```language
<必要时提供示例代码>
```

**预防措施**：

- <与当前问题相关的预防措施>
````

标题信号灯与 severity 一致：fatal=🔴 Fatal、major=🟠 Major、minor=🟡 Minor、suggestion=🟢 Suggestion。位置使用仓库相对路径和明确行范围，影响与建议应有证据，不强制方案数量。

页面、正式合同和报告保留原始 body，处理决定不改变正文。发送只传 severity/body，不夹带内部证据、规则或执行记录。发布适配将换行统一为真实 CRLF，完整正文作为单个 argv 值传给 CLI；序列化转义符不应变成正文中的字面 `\r\n`。

### 5.3 状态与报告

数据位于 `%LOCALAPPDATA%/ReviewX`，使用文件持久化及短时锁、原子替换，不引入数据库。

- `state.json` v1 保存项目顺序、MR 快照、队列、全部 attempt、Finding 决策、发布批次和诊断。损坏或未知版本不得初始化为空。
- `reports/<attemptId>/report.md` 保存 attempt/Project/MR 标识、版本与分支、固定 SHA、PASS/FINDINGS 和按序完整正文。
- 同目录的 `submission.v1.json` 保存正式合同；`execution.v1.json` 保存范围、规则快照、实际模型、会话、收据哈希、权限摘要及终态。独立文件不要求迁移 state.json。
- `logs/` 保存每次服务日志；`workspaces/` 保存临时 Git 对象和可信任务目录，执行结束清理。

每次成功 attempt 有独立不可变报告，即使 MR 版本相同也不覆盖。文件写入后必须成功登记状态引用；登记失败是不可发布的孤立产物，不自动恢复为成功。报告与日志读取校验受控引用、规范路径和真实路径，禁止任意文件访问。

兼容旧单/多条发布记录，保留 ordinal、commentId、决策和正文；缺少独立执行文件的历史 attempt 仍可读取，显示执行信息不可用。回滚不得用旧状态备份覆盖新增发布记录。兼容范围不意味着所有缺字段的 v1 文件均可启动，项目地址要求见 3.1。

## 6. 安全、日志与故障

### 6.1 执行与访问边界

HTTP 只监听 loopback，不启用 CORS；状态变更校验精确 Host、同源 Origin、JSON 类型和大小，详见 API。MR 标题、路径、CLI 输出与模型正文均是不可信输入。

子进程通过参数数组调用，不拼接 shell。Windows PowerShell shim 使用 JSON 参数信封保留换行、引号和反斜杠，不拆分正文参数。

OpenCode 仅使用 1.18.30 HTTP + Node fetch 接入，不指定 model/provider/variant，不使用 SDK 或聊天结果回退。保留原生认证、配置路径及必要企业网络环境，不重定向 HOME、不复制认证、不改写用户持久配置。

每个 attempt 使用可信任务目录、随机 loopback 凭据和绑定会话的工具桥接。除六个 ReviewX 工具外均禁止，包括 shell、编辑、任意网络与 CodeHub 写入。仓库指令、Skill、插件和配置仅是待检视数据，不自动执行；读取不触发仓库 LSP、formatter 或脚本。检测不兼容的额外配置、全局工具、启用的 MCP 或指令时，在交付材料前失败。

这些是应用层约束，不是 OS 沙箱，也不承诺阻断所有扩展初始化。OpenCode 原生会话可能留存交付材料，ReviewX 不删除其整个数据目录。默认日志和执行摘要不保存完整源码、工具正文、推理、用户配置或认证；正式 Finding 正文和冻结规则按结果契约保存。交付前执行敏感输入检查，诊断中的凭据必须脱敏。

项目网页地址的原样字符串处理见 3.1，不能据此宣称所有外部地址都经凭据过滤。Markdown 单独执行安全渲染：禁用原始 HTML、脚本、表单、嵌入内容和危险 URL；图片只显示经公共 HTTP(S) allowlist 校验的链接，不自动加载本地或私网资源。

### 6.2 日志与错误

每次服务创建永久纯文本日志。终端启动时输出地址和日志路径，运行进度写日志并同步简化网页状态。日志使用英文自然语言和本地时间 `YYYY-MM-DD HH:mm:ss.SSS`，附 Project/MR/attempt/Finding 上下文；动态文本控制字符转义、凭据脱敏，不能伪造日志行。

同一错误在最具体阶段记录一次，包含 Cause、Impact、Next step、Technical details。非空 stderr 脱敏并去除 ANSI；非预期内部错误附脱敏 stack。用户主动停止是正常结果，仍记录阶段与清理。

| 故障 | 影响 |
| --- | --- |
| 添加项目失败 | 只影响本次添加 |
| 刷新失败 | 停止本次刷新，未完整取得的数据不覆盖快照 |
| 检视失败 | 当前失败，清空等待队列，不影响评论通道 |
| 评论失败/未知 | 只终结目标 Finding，不自动补发 |
| 报告或状态登记失败 | 不开放处理或发布入口 |
| 运行期日志不可写 | 进入致命状态，拒绝新刷新、检视和发布，仍允许停止与移除 |

## 7. 验收标准

| 类别 | 必须验证的结果 |
| --- | --- |
| 启动与安装 | Windows 隔离安装、含空格路径、非仓库 cwd、随包规则/字体/许可证、随机 loopback、单实例、浏览器失败降级及重启 |
| 项目与发现 | ID/CLI 校验、项目与 MR 地址差异、树导航、手动刷新原子性、移除和重新添加保留历史，无自动发现或检视 |
| 调度与恢复 | FIFO、同 MR 活动门禁、同版本重新检视、立即归档、取消清理、失败队列、重启不续跑及保存/取消竞态 |
| 版本与证据 | T≠B、两次 MR 检查、删除/重命名基线、未修改调用方、分页、错误修订与未交付行拒绝、关键缺口不误判 PASS |
| 提交与终态 | 合法空结果、无效/缺失/冲突提交、重复事件去重、错误会话、提交后取消/错误/超时/断流/未知终态均不产生错误成功 |
| 规则与安全 | 默认语言/项目选择、资源缺失越界、冻结不漂移、原生环境兼容、敏感输入、链接/junction、间接执行与权限拒绝 |
| 人工处理 | 单条发送/跳过/撤销、历史只读、发送互斥、检视与发布独立、failed/unknown 归并、不补发、不做发布前版本检查 |
| 正文与文件 | 中文、换行、代码块、反斜杠和尾随空白保真，发送仅 CRLF 转换；不可变报告、受控读取、孤立产物不可发布 |
| 网页可用性 | 轮询不重叠、详情随 revision 更新、耗时固定、报告按需缓存、外链隔离、弹窗/抽屉焦点与滚动、日志阅读和 Markdown 安全 |
| 真实闭环 | 源码与安装包引擎分别使用原生默认模型完成读取、正式提交和执行核对，人工复核意见依据，技术成功不替代质量判断 |

验收使用合成仓库，不向真实 CodeHub 发布测试评论。协议、状态和竞态采用确定性测试；桌面浏览器保护业务、键盘、焦点、滚动与导航，不以手机或精确视觉矩阵为门槛。真实模型与 Windows 环境验证分别记录，不能外推所有版本、模型或缺陷召回率。

每轮改动执行完整质量检查及源码/安装包真实模型验收，命令与产物入口统一见 [README](../README.md#源码开发)。记录环境、命令、结果、失败或未执行原因、证据位置及正文复核结论；历史通过不能替代当前验证，任一步未通过不得宣称整体验收通过。
